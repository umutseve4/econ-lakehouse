# Contributing

Thanks for helping improve this project.

1. Open an issue first for security-sensitive, breaking, or broad architectural changes. Report vulnerabilities privately as described in `SECURITY.md`.
2. Create a focused branch from the current default branch and keep the pull request limited to one concern.
3. Follow the setup and validation commands documented in `README.md` and the repository workflows. Add or update tests when behavior changes.
4. Do not commit credentials, tokens, private data, generated secrets, or local environment files.
5. In the pull request, explain the problem, the chosen approach, exact validation commands and results, and any remaining limitations.

Pull requests should keep dependencies and lockfiles synchronized, avoid unrelated formatting churn, and preserve backward compatibility unless a breaking change has been explicitly agreed.
